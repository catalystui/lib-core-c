# AGENTS.md

Repository-wide requirements for CatalystUI Core, including implementation, documentation, tests, and builds.

## Authority and scope

- Core provides foundational, language-independent C ABI libraries based on FDEFSPEC (Foundational Definitions Specification), independent of CatalystUI layers, domains, operating systems, and languages.
- The owner defines architecture and contracts. Do not invent or reinterpret them. Before changing existing foundational code, APIs, representations, or behavior (including fixes, refactors, signatures, and new helpers), explain the change, necessity, and consequences and obtain explicit approval. Approval covers only the requested scope.
- Core is in early development. Backwards compatibility with earlier Core revisions is not required: existing source signatures, binary layouts/exports, result codes, and behavior are not frozen solely because they already exist. Prefer the correct approved design over legacy compatibility; do not add compatibility shims, deprecated variants, or parallel APIs merely to preserve old callers. Update affected implementations, callers, tests, and documentation together. This does not waive FDEFSPEC, C interoperability, 8-bit compatibility, or owner approval for changes to foundational contracts.
- Never modify or bypass Numeric Definitions, Codepoint, Text Encoding, or Operation Status to simplify another implementation without approval.
- Prefer simple, direct, explicit code; avoid speculative abstractions, unnecessary dependencies, convenience APIs, duplicated algorithms, and unrelated cleanup.
- `README.md` is for humans only; neither use it as development context nor edit it without explicit request. Consult specifications, headers, implementations, references, and tests.

## Mandatory 8-bit compatibility

Every Core library MUST be implementable and usable on an 8-bit system.

- All arithmetic, including intermediates, must require at most eight bits. Use `CATALYST_BYTE` / `BYTE` or `CATALYST_SBYTE` / `SBYTE`; represent larger logical values as ordered bytes. Implement carry, borrow, shifts, comparisons, multiplication, division, and overflow checks byte-by-byte; mask before shifting. Never rely on widened intermediates, including implicit C/C++ integer promotions.
- Never pack bytes into native wider integers for computation, comparison, shifts, encoding, or decoding, even through casts, unions, reinterpretation, intrinsics, library calls, or conditional fast paths. Core algorithms must not require native floating-point arithmetic.
- Preserve explicit byte order; assume no host endianness, alignment, pointer width, or native integer layout. Never serialize native structs/integers in place of specified byte representations.
- Reference: `src/cattelib.cpp` implements Codepoint and Text Encoding byte-wise. `CATALYST_CODEPOINT` uses MSB-first `byte0`–`byte3`; `CATALYST_UTF16LE_CODE_UNIT` uses `lsb`, then `msb`.
- Preserve the pointer-width ABI of `CATALYST_NINT` / `CATALYST_NUINT` for addresses, addressable sizes, counts, and indices, including one-byte pointers. Never use them to bypass byte arithmetic or assume a wider minimum. Report existing native-width arithmetic conflicts and obtain approval before changing them.
- Wider numeric types and existing guarded C++ native-integer constructors, assignments, and conversions are optional conveniences, not algorithm prerequisites. Preserve `CATALYST_SUPPORTS_*` guards; do not use these conveniences in Core algorithms, extend them, or add native conversion helpers without approval.
- Confine unavoidable native platform API types to platform backends. Obtain approval for new exceptions or resolutions of byte-arithmetic conflicts.

## Language and ABI

- Public C headers: C90. Implementations/wrappers: C++98. Newer standards are optional through existing guards.
- Maintain a C ABI (not backwards binary compatibility between development revisions): `include/<library>.h`, `src/<library>.cpp`, thin inline `include/<library>.hpp` wrappers; retain include guards, `extern "C"`, and export macros.
- Use Catalyst types, not language-specific containers, exceptions, references, native booleans, or unguarded fixed-width types. Use `CATALYST_BOOL` / `BOOL` and `TRUE` / `FALSE`.
- Select return conventions using the mandatory Function classification and reporting rules below. C++ wrappers preserve the C contract and forward without duplicating logic.
- Preserve read/write pointer distinctions (`const`, e.g. `CATALYST_UTF8` vs. `CATALYST_UTF8W`), opaque handles with private implementation storage, ownership, lifetime, alignment, allocation, and buffer contracts.
- Use CATMMLIB for shared allocation/byte operations where appropriate. OS calls belong in `*.win32.cpp`, `*.linux.cpp`, or `*.darwin.mm`. No STL containers, heap abstractions, or external dependencies in portable Core without approval.

## Naming and style

- C types/constants: uppercase snake case, `CATALYST_` prefix. C functions: lowercase snake case, library prefix + subject + operation (e.g. `catmm_copy`, `catte_utf8_encode`, `catrl_array_create`). Reserve `cat_` for existing foundational patterns; new foundational functions require approval.
- C++ types/constants omit `CATALYST_`; functions omit library prefix, all in `namespace catalyst`. Public parameters/fields and generally private functions use lowercase snake case; existing descriptive lower-camel-case locals are acceptable. Match surrounding code; avoid unrelated renames.
- Four-space indent, same-line braces, `if (...) {` / `} else {`, null pointer `0`, C-compatible `typedef`, existing explicit casts (e.g. `(BYTE) 0x80`).
- Use early returns, direct control flow, named byte values, simple loops, and `static` for private helpers. Follow section dividers and concise `//` comments explaining intent, bit layouts, nonobvious conditions, internal state guarantees, and failure stages—not obvious assignments.
- Follow `.editorconfig` and `.gitattributes`: UTF-8, CRLF working-tree endings, final newline, no trailing whitespace.

## Validation boundary

- Core is a foundation of computing primitives, not a defensive programmer-validation layer. Every public function and private helper assumes that its documented caller preconditions hold. The caller owns contract validation: live and correctly typed handles, initialized objects, valid readable/writable pointers and extents, required termination, valid indices for direct indexed access, nonzero configured element extents, lifetime, alignment, non-overlap, synchronization, and any other prerequisites of the operation. Do not check these again in Core or return Results for their violation. A contract violation is outside the function's guarantees.
- Core owns operational validation: conditions that determine whether the intended operation can succeed even with all caller preconditions satisfied. Examples include malformed encoding encountered during decoding, unrepresentable codepoints, supplied capacity limits, requested extent overflow, allocation/native I/O/cleanup failures, and missing keys or empty stacks when the requested retrieval cannot produce a value. Do not require input content to be well-formed if determining its meaning is the operation's purpose.
- Perform necessary checks as part of the actual operation, not a separate preliminary validation pass. Bounds checks needed to read a malformed sequence safely are operational; a caller must supply an accessible extent or terminated sequence according to the documented interface. Never read beyond that extent. Do not hide an operational failure by redefining it as a precondition.
- Establish valid internal state during creation and preserve it through mutation. Trust live handles and the guarantees established by previous operations; do not repeatedly inspect storage metadata or revalidate internal steps solely to detect programmer misuse or arbitrary memory corruption. Detect genuine failures of internal state arising from an operation or dependency when they can occur with valid inputs.
- Ordinary absence, empty state, comparison, arithmetic carry/borrow, and no-op are normal outcomes when so defined. Do not introduce validation or reporting merely to acknowledge them. Define the natural contract first, then choose the return type.
- These rules apply equally to C exports, C++ wrappers, and internal helpers. The owner has approved applying this validation policy to existing Core functions and removing redundant checks and Results; unrelated architectural changes still require approval.

## Function classification and reporting

Classify every public function and private helper by its intended, approved contract, in this order. Existing signatures, result assignments, and tests are evidence of current behavior, not justification for retaining unnecessary reporting. Apply the validation boundary above; do not retain previous caller-contract checks for backwards compatibility. Other changes to intended operation semantics require owner approval. Apply the first matching rule:

1. **Reportable operation:** If the function must distinguish a warning, error, or fatal outcome from ordinary successful behavior, return `CATALYST_RESULT` (C++ wrapper: `RESULT`) by value. Return any additional data through output arguments.
2. **Non-reporting value function:** Otherwise, if the function produces a single ordinary value, return that value directly using its Catalyst type. This includes computations, predicates, accessors, comparisons, and conversions that are total over their documented input domain.
3. **Non-reporting procedure:** Otherwise return `void`; write any necessary outputs or mutate existing storage through arguments. Multiple outputs alone do not justify a Result.

Apply these rules consistently:

- A reportable outcome exists when the contract requires detecting operationally invalid data, malformed input, insufficient capacity, overflow, allocation or dependency failure, unsupported operations, or another meaningful warning/error/fatal condition. Allocation, external I/O, and other operations with recoverable runtime failures must report. Do not classify an operation as infallible merely because failure is rare.
- Ordinary domain values (false, zero, equality, empty, or absence when explicitly defined as a normal lookup outcome) are not reportable failures. Do not invent sentinel errors, warnings, or success-only Results to justify reporting or avoid a required Result. A no-op alone does not require reporting; a reporting operation still follows its approved no-op contract.
- Document caller preconditions for both public and private functions. Do not provide parallel checked variants merely to validate compliance with the calling contract.
- Report at the outermost boundary that owns operational validation, failure handling, and the operation's observable contract. Perform necessary operational checks once where sufficient; use non-reporting primitives for subsequent steps whose preconditions are established. If an internal step can still fail or warn and its caller must distinguish that outcome, it must report. Never suppress a required diagnostic to improve performance.
- Hot-path frequency, function length, loop count, and scalar/buffer classification do not override these rules. For example, a total byte computation returns a byte, a buffer copy or mutation over valid storage returns void, and allocation returns a Result. A checked scalar conversion reports if malformed input or overflow must be distinguished.
- For reporting functions, return the four-byte Result directly on every exit; never accept a Result output pointer, use shared last-result state, or combine data and Result into a larger return structure. Use ordinary output arguments for data, and document their validity on each outcome. Preserve existing approved result semantics and byte-only construction.
- For non-reporting functions, do not construct, propagate, or document a Result. Tests and references must reflect the selected convention and documented preconditions.
- Performance target: aim for less than 10% additional execution time at a reporting boundary; 20% or more is a review trigger, not permission to remove required reporting. Benchmark representative hot paths against equivalent non-reporting work, including output storage and status consumption; report absolute time and call frequency as well as relative overhead. Static instruction counts are not execution timings. Do not impose a universal instruction-count or workload-size cutoff. If required reporting is costly, propose moving validation/reporting to an enclosing boundary or restructuring the algorithm, and obtain approval before changing existing contracts.
- When adding or reviewing a function, identify its ordinary outputs, preconditions, and reportable outcomes before choosing its signature. If the contract is ambiguous or conflicts with an existing approved signature, ask the owner rather than guessing.

## Operation results

`CATALYST_RESULT` / `RESULT` is four ordered bytes: status, context, operation, detail. Each has a distinct scope and purpose; never pack into a native integer or substitute exceptions/ad hoc conventions.

- **Status (universal):** Outcome, analogous to HTTP status. Use the most specific applicable FDEFSPEC code. Undefined codes are reserved; never add or redefine them without approval.
- **Context (unique per module):** Execution context, normally a stable ID identifying the method within its library/module. Locates the result's origin, not the internal failure stage. MUST identify the reporting method on every returned Result, including all Success-level statuses (including no-op), warnings, errors, and fatal outcomes. Use the same assigned context ID on every return path; zero is reserved for an unspecified context, not for successful outcomes.
- **Operation (unique per method):** Identifies the precise internal operation/result-reporting site, not the public method or a generic error category. Assign a different opcode to every distinct result assignment site within a method, including success paths; never reuse an opcode across sites even when their statuses or failure reasons match. A single site may report multiple detail values. Keep IDs consistent and documented within the current revision; backwards compatibility does not require retaining obsolete IDs or gaps.
- **Detail (scoped to operation):** Additional useful information for the status/context/operation combination. May be symbolic, a literal byte value, an index, a count, or zero when nothing further is needed. Meaning precedence: status > context > operation; never override a higher-priority definition. Do not duplicate information already conveyed by other bytes or force runtime data into detail.
- `ERROR_INVALID_ARGUMENT` detail MUST be the zero-based argument index from the full public function signature (including by-value arguments). Zero is meaningful here.
- Define/document context IDs, opcodes, and applicable detail meanings consistently within their scopes before implementation. Example: UTF-8 decoder context identifies the method; each continuation check has its own opcode; detail may be zero or the offending byte if useful. Distinct missing-unit cases at one unexpected-end check may use distinct symbolic details.
- Dependency failures: retain the reporting method's context and exact call-site opcode; report the actual applicable status and useful detail without blindly copying dependency fields or defaulting to `ERROR_DEPENDENCY_FAILURE`. Preserve meaningful diagnostics and fatal severity when applicable; respect status-defined detail. Changes to existing result contracts require approval.
- For reporting functions, return all four fields by value on every path using `return RESULT(...);` in C++ implementations, defined status constants and severity helpers. Never invent information solely to avoid zero.

## Correctness

- Assume documented caller preconditions. Check only operational conditions, before unsafe reads/writes or irreversible changes as applicable; preserve documented failure-output behavior and other operational guarantees.
- Check operational overflow, capacity, bounds, allocation failures, malformed input, and dependency results when necessary for the intended operation. Preserve logical state on recoverable mutation failure where promised; clean up resources and report cleanup failures accurately.
- Distinguish bytes, code units, codepoints, terminators, and BOMs; preserve text buffer, substitution, and invalid-input contracts.
- Report existing implementation/reference conflicts with these requirements; do not treat them as precedent or fix them outside an approved task.

## Documentation

- Specifications define concepts; explanatory docs teach them; API references describe precise contracts for lookup. Keep headers, wrappers, implementations, references, and tests consistent with approved contracts.
- Each public declaration gets a short `/** ... */` comment describing behavior and essential preconditions/output behavior, not a duplicate reference.
- API Reference: `docs/lang/en-US/api-reference/index.md` and one comprehensive `api-reference/<module>/index.md` per module (CATALYST, CATMMLIB, CATTELIB, CATRLLIB); update `docs/manifest.json` for navigation changes. Module pages cover headers, namespace, actual linker name (**Library:**), library dependencies when applicable (**Dependencies:**), types, constants, exports, and all functions. Use Header-only for modules that require no linked library. Public documentation consists of a README-aligned Overview, its Assumptions child page explaining the validation and reporting principles, and the API Reference, with API Reference last in navigation. Adapt README content to the documentation site when updating the Overview; do not modify README.md without explicit request. Keep Assumptions aligned with the Validation boundary and Function classification and reporting rules. Do not duplicate API contracts in separate topic pages. Add tutorials, usage guides, or other explanatory documentation only when explicitly requested or approved; place them before the API Reference. Do not add module-level Conventions sections. Document unique contractual details at the relevant type, function, parameter, or narrowly scoped function group. Define shared behavior once and avoid repeating the Assumptions page, signatures, result tables, or generic result-pattern notation. Omit obvious cross-module links, generic explanations of the reference format, and redundant prose; retain precise contracts and useful targeted See Also links.
- Javadoc-inspired module structure: introduction with relevant header/type; **Function Summary** table of linked exact C function names and brief descriptions; **Function Details** with each exact function name as a heading, exact C signature in a fenced `c` block (multiline when long), natural description, **Parameters:** with individual names/descriptions (no parameter table), **Results:** table, and **See Also:** links when useful. Add Type/Constant Summary and Details when applicable. In Type Details, place the natural description immediately after the heading (then any availability badge), followed by the C typedef declaration or representation table, field details, and C++ equivalent; use consistent field formatting; use **Returns:** for directly returned values, **Results:** for directly returned `CATALYST_RESULT` values. Reference current implementation and approved contracts; never document proposed result assignments as current behavior. For conditional definitions, use a standalone `<span data-heading-badge="MACRO" data-heading-badge-background="#b4232c" data-heading-badge-color="#ffffff" title="Requires MACRO to be 1"></span>` after the heading or its description; no separate REQUIRES paragraph. The renderer moves markers into the preceding heading without changing anchors. Other badges may specify their own background, text color, border (`data-heading-badge-border`), radius (`data-heading-badge-radius`), and tooltip (`title`). Where types differ by C version, use **C90:** / **C99+:** qualifiers followed by fenced `c` typedef declarations, with `#if CATALYST_SUPPORTS_*` guards for optional types (not `#ifdef`; support macros can be zero). State unavailable variants explicitly. Use Markdown hard line breaks between consecutive metadata or parameter/field entries instead of separate paragraphs; keep **See Also:** as a separate paragraph. Link specifications to the live CatalystUI website.
- For reporting methods, document each method's assigned context once as **Context:** `0xCC` immediately before **Results:**; every returned result carries that context byte, including success-level results. Results tables have exactly four columns: `Result | Status | Operation | Detail`. One row per distinct result, including each fixed detail value. First column: complete hexadecimal `0xSSCCOODD` (uppercase digits, status–context–operation–detail order regardless of host endianness). Other columns explain status, operation, and detail without restating byte values unnecessarily. Use an em dash only for truly unused fields, not meaningful zero values. Never group distinct fixed results in one row/cell.
- For genuinely variable fields, document exact byte ranges/patterns and meanings instead of inventing fixed codes or omitting values. Hex notation does not imply native integer packing.
- Explicitly document units, capacities, nullability, ownership, failure outputs, edge cases, and observable guarantees. Use exact Catalyst terms/identifiers, concise readable prose, and tables for lookup or relationships—not implementation narration. No unsupported promises, FDEFSPEC changes, or silent reconciliation of discrepancies.

## Build and verification

- Preserve shared CMake infrastructure, `cmakecfg.h`, and static/shared targets. Initialize `cmake` submodule recursively; use existing presets. Do not change submodule, build configuration, or CI to work around code issues without approval.
- Runtime binaries (executables/tests, Windows DLLs, Unix versioned shared libraries and ABI aliases) go directly in `debug/` or `release/`; development linker inputs (static archives, Windows import libraries and unversioned Unix linker aliases) go in its flat `lib/` directory. Unix runtime dependencies resolve relative to the binary; development aliases point to the runtime ABI aliases. No separate test/import-library directory. Preserve formal library names, headers, and CMake targets; artifact bases: `catmm`, `catte`, `catrl`. Shared `build-cmake` owns naming/versioning, derived from project metadata.
- Example v1.5.2 (`catmm`):
  - MSVC: `libcatmm.lib`, `catmm.lib`, `catmm15.dll` (full version in DLL resource).
  - Linux: `libcatmm.a`, `libcatmm.so`, `libcatmm.so.1.5`, `libcatmm.so.1.5.2`.
  - macOS: `libcatmm.a`, `libcatmm.dylib`, `libcatmm.1.5.dylib`, `libcatmm.1.5.2.dylib`.
  - Unix linker/ABI aliases are symlinks.
- Use existing standalone `test/test_<library>.cpp` programs, exercising C++ wrappers and checking ordinary outputs and, for reporting functions, all four result bytes. Cover normal, boundary, no-op, malformed data, operational overflow, and failure-state cases as applicable; do not invoke functions in violation of caller preconditions; simple checks/nonzero exits, no new test framework.
- Verify public headers/builds with C90/C++98 and C99/C++11 when possible. Independently review byte arithmetic and width assumptions; x86/x64 builds do not establish 8-bit compatibility. Never claim actual 8-bit testing unless performed.
- Report tests performed, limitations, and conflicts with requirements.
